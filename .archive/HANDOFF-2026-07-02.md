## 0. Thèse fondatrice (à mettre dans VIS-LLL-001 réécrite)

Langage de programmation 100% dédié au coding par agents LLM — pas à l'ergonomie humaine en premier lieu. Thèse opérateur : les langages existants ont des défauts pour le coding par LLM ; les gros projets sont difficiles à maintenir ; refactorer coûte cher spécifiquement en TOKENS ; tout se résume à l'efficience de l'échange de tokens, qui plafonne ce qu'un LLM peut faire dans un contexte fini. Non négociable : compilé, aussi rapide que le C à l'exécution ; taille binaire/stockage non-critère.

**Directive gouvernante (la plus importante)** : "On livre le langage complet, pas à 60%. On ne va pas créer un truc qui pose des problèmes, et s'il faut développer un peu plus, on développera un peu plus, c'est absolument pas ça qui nous fait peur." → aucune fonctionnalité sciemment incomplète/incohérente pour aller vite. Investir plus de temps de conception est explicitement acceptable.

**4 critères directeurs** (à respecter dans TOUTE proposition future) :
1. Empreinte contexte LLM aussi faible que possible (minimiser le nombre d'endroits à lire pour comprendre/modifier en sûreté).
2. Gros projet : redondance quasi nulle, DRY strict, une seule source de vérité par concept.
3. Facilité de maintenance PAR UN LLM en priorité (pas par un humain en premier lieu).
4. Canal d'explicabilité : mécanisme (pas forcément dans le code) pour qu'un humain comprenne l'exécution et serve de support/audit au LLM (pas de confiance aveugle), et pour que le LLM communique sa démarche.

Équipe : solo (opérateur) + jusqu'à 10 agents LLM en parallèle, pas d'autre humain, pas de deadline fixe.

## 3. Itérations de syntaxe (historique, pour comprendre pourquoi la forme actuelle est ce qu'elle est)

1. **Strawman 1** (rejeté) : `fn name(arg: Type) -> Ret`, `pre`/`post`, `!` pour effets, pipe `|>`. Opérateur : "ça ne me plaît pas, je veux du Elixir/Python-indent/type-first/pure/DDD."
2. **Strawman 2** (rejeté) : Elixir-lecture (`def`, `|>`, `case`) + indentation Python + ligne de type séparée `::` (Haskell-style) + `domain X.Y:`. Opérateur d'accord sur le style mais "pas optimal pour un LLM au niveau structure."
3. **Auto-correction importante** : j'avais recommandé des délimiteurs explicites (`end`) contre l'indentation pure en invoquant "Python 6% erreurs syntaxe vs Go 25%" — **donnée confondue par le volume de corpus d'entraînement, pas une preuve indentation-vs-délimiteurs propre**. Les vraies études (arxiv 2503.01245) montrent que les erreurs SÉMANTIQUES dominent largement les erreurs syntaxiques (<10% du total) chez les LLM — le vrai levier de fiabilité est la désambiguïsation d'intention (contrats), pas le style de bloc.
4. **Recherche large demandée par l'opérateur** → trouvé Bosque, AIDL, Lisp/homoiconicité (§1, items 8-10).
5. **3 variantes comparées** (Lisp, Bosque-`requires`/`ensures`, AIDL-`constrain`/`yield where`) → opérateur choisit **AIDL** mais me demande une auto-évaluation honnête. **3 doutes identifiés et corrigés** : (a) asymétrie `constrain`(ligne séparée)/`where`(accolé en fin de `yield`) → remplacé par `requires`/`ensures` symétriques (repris de Bosque) ; (b) cérémonie vide si `constrain` obligatoire même sans contrainte réelle → rendu optionnel ; (c) pas de construction pour étapes intermédiaires nommées → ajout de `let`.
6. **Syntaxe verrouillée = DEC-014** (voir code ci-dessous), puis extension flux général (type/match/récursion/combinateurs) présentée et globalement acceptée, avec un doute explicite sur `measure` (résolu en §4, rapport agent).

### Exemple verrouillé (DEC-014, base)

```
module Pricing.Quote:

  part discount(price, pct) -> Float:
    requires price >= 0, 0 <= pct <= 1
    ensures  result >= 0, result <= price
    yield price * (1 - pct)

  part price_lookup(sku) -> Result[Float, HttpError] via IO.Http:
    requires sku.len > 0
    let raw = Http.get(f"catalog/{sku}/price")
    let val = raw.field("price")
    yield val

  part quote(sku, pct) -> Result[Float, HttpError] via IO.Http:
    requires 0 <= pct <= 1
    let price = price_lookup(sku)
    yield price.map(discount(_, pct))
```

### Exemple étendu (flux général — type/récursion/pattern-matching/combinateurs)

```
module Domain.Tree:

  type Tree[T]:
    Leaf
    Node(value: T, left: Tree[T], right: Tree[T])

  part sum(t: Tree[Int]) -> Int:
    match t:
      Leaf          -> yield 0
      Node(v, l, r) -> yield v + sum(l) + sum(r)

  part gcd(a: Int, b: Int) -> Int:
    requires a >= 0, b >= 0
    measure b
    match b:
      0 -> yield a
      _ -> yield gcd(b, a mod b)

  part classify(n: Int) -> String:
    match n:
      0             -> yield "zero"
      n when n > 0  -> yield "positive"
      _             -> yield "negative"

  part total(prices: List[Float]) -> Float:
    yield prices.fold(0.0, fn(acc, p) -> acc + p)

  part midpoint(p1: Point, p2: Point) -> Point:
    let Point(x1, y1) = p1
    let Point(x2, y2) = p2
    yield Point((x1 + x2) / 2, (y1 + y2) / 2)
```

Principes : récursion structurelle vérifiée par défaut (décroissance sur sous-terme, à la Agda/Idris/Coq, zéro solveur) ; récursion non-structurelle nécessite `measure` (voir §4 pour le niveau de vérification définitif) ; combinateurs map/filter/fold = idiome PAR DÉFAUT pour itération sur collections finies, récursion réservée aux structures réellement récursives.

### 4.1 Vérification contrats & terminaison (→ DEC-015, DEC-016, DEC-017)

- **Terminaison, statique et obligatoire, séparée du contrat fonctionnel** : récursion structurelle (défaut, zéro solveur, analyse syntaxique décidable) ; `measure e` pour récursion non-structurelle → obligation `measure[args_récursion] < measure[args_courants]` en ordre bien-fondé, **déchargée par Z3** (= `decreases` de Dafny). Non déchargé ⇒ erreur de compilation. Jamais "parsé mais non vérifié".
- **Couplage clé** : la preuve de terminaison permet d'ASSUMER le contrat de l'appelé à un site récursif (mécanisme Dafny) = induction gratuite sans tactique, sans Lean nécessaire pour l'essentiel.
- **Contrats fonctionnels — Z3 sur fragment DÉCIDABLE volontairement restreint** : LIA/LRA, booléens, égalité, UF, constructeurs/sélecteurs ADT natifs Z3, quantification BORNÉE sur collections finies (désucrée en fold/all/any, jamais ∀ non borné). Non-linéaire autorisé mais timeout dur ; échec ⇒ erreur exigeant un hint `proof` (étapes assert/lemme façon Dafny), jamais de downgrade silencieux runtime. Leçon directe de l'échec GRAPHE (timeout Z3 sur formules trop générales).
- **Runtime SEULEMENT à la frontière FFI/effet** (où une valeur externe entre dans le monde vérifié — le compilateur ne peut statiquement savoir qu'elle satisfait le contrat) : validation retournant `Result` (parse, don't validate). Cœur pur : tout statique, contrats effacés en release (zéro coût, vitesse C).
- **Intégration pipeline MLIR→Rust** : fork propre — `core` (typé HM+effets) → [FORK VÉRIF] `vc` → SMT-LIB → Z3 (verdicts seuls, aucun code émis) ; `core` → [FORK EXÉC] `eff` → cps/fsm → mem(Perceus) → rust → rustc. Le fork exécutable efface contrats+proof steps, ne voit jamais Z3.
- **Vérif incrémentale** : cache par `(hash_définition, hashes_des_CONTRATS_des_dépendances)` — pas les corps. Modifier un corps ne re-vérifie que cette définition ; modifier un contrat ne re-vérifie que les appelants directs.

### 4.2 Système de types complet (→ DEC-018)

- **Cœur HM étendu** : Damas-Milner + inférence bidirectionnelle aux frontières `part` + **row-polymorphism pour les effets** (`via IO.Http`, approche Koka/Frank/Effekt). Génériques = polymorphisme paramétrique HM standard, inféré.
- **Raffinements VÉRIFIÉS, jamais inférés** (explicitement PAS de Liquid Types — trop de complexité, même piège que GRAPHE).
- **Transpilation Rust** : monomorphisation agressive par défaut (taille binaire non-critère) ⇒ vitesse C, dispatch statique. `dyn`/trait objects seulement pour existentiels rares. **Sans GC mais fonctionnel pur** : reference counting (Rc/Arc) + analyse de réutilisation Perceus/FBIP (Lean4, Koka) — passe `mem` transforme les updates en mutations in-place quand compteur=1. La preuve (fork `vc`) opère sur `core` AVANT monomorphisation ⇒ une preuve pour toutes les instances.

### 4.3 Modules / imports gros projet (→ DEC-019 / DEC-020)

- **Modules = overlay de nommage à poids sémantique nul.** Identité réelle = hash Blake3 de l'AST normalisé (variables en de Bruijn, noms effacés du hash). Renommer ne change pas le hash (rename gratuit dans le CONTEXTE LLM — précision honnête : le texte disque change bien, c'est la commande structurelle qui fait la réécriture mécanique déterministe sans que l'agent lise/réécrive les sites d'appel). Déplacer entre modules ne change pas le hash. **Deux définitions identiques = même hash = déduplication automatique** ; egglog détecte aussi l'équivalence sémantique (pas juste syntaxique).
- **Texte = source unique de vérité** ; graphe + couche de noms + caches de preuve = tous DÉRIVÉS du texte, reconstructibles (`llmlang index`). Cycles d'imports = non-problème (le graphe de dépendances est au niveau définition, pas fichier).

### 4.4 Canal d'explicabilité (→ REQ-LLL-002, nouvelle exigence, jamais persistée en SOLL faute d'Axon dispo)

4 couches, toutes clés par content-hash, TOUTES hors du texte source (ne pas re-humaniser la syntaxe, DEC-013 préservé) :
1. **Rationale (design-time)** : par définition, sidecar clé-par-hash (intention, alternatives écartées, liens REQ/DEC). Si le corps change (nouveau hash) → l'ancien rationale se détache automatiquement, dérive doc/code impossible par construction.
2. **Journal de décision (dev-time, append-only)** : log immuable des mouvements LLM, lié aux commits git. **Recommandation : matérialiser via la couche SOLL Axon elle-même** (decisions/requirements/concepts), pas réinventé.
3. **Trace d'exécution (runtime)** : seuls les effets sont tracés (le cœur pur est rejouable depuis entrées+résultats d'effets, référentiellement transparent). Replay déterministe, time-travel. Émergent de la pureté+effets, pas un ajout.
4. **REPL d'audit humain, lecture seule** : sur {hash-graph+types+contrats+rationale+journal+traces}. **Recommandation : extension d'Axon MCP** (why/impact/inspect/retrieve_context) plutôt qu'un système parallèle.

### 4.5 Concurrence multi-agents fine (→ DEC-023, complète DEC-007)

Unité de changement = la DÉFINITION (par hash), pas le fichier/la ligne. Définitions différentes = jamais de conflit (hashes disjoints, union du graphe). Store adressé par contenu = immuable/append-only = MVCC gratuit. **Vrai conflit = un même NOM résout vers 2 hashes** (détection triviale) → présente les 2 corps+rationales+verdicts à un arbitre. **Le contrat = pare-feu de concurrence** : modifier le CORPS de `discount` n'invalide pas le travail sur `quote` (dépend seulement du CONTRAT de `discount`, stable). Verrous fichier GUI-PRO-104 = garde-fou pessimiste immédiat + fallback nommage partagé, le merge hash-graph = mécanisme optimiste par défaut.

### 4.6 Séquençage (→ DEC-024, reformulé par l'opérateur ensuite, voir §5)

Recommandation initiale de l'agent (85% confiance) : "prototype jetable" avant tout. **REJETÉE PAR L'OPÉRATEUR EN AVAL** (voir §5) — reformulée en "noyau v1, périmètre étroit, rigueur totale", PAS de label "jetable"/"prototype"/"draft". Les 4 cibles de falsification de l'agent restent valides comme SCOPE (pas comme excuse de qualité réduite) :

### 4.7 Points réellement ouverts (honnêteté de l'agent, non résolus)

1. Non-linéaire/induction profonde hors Z3 : pencher pour INTERDIRE en v1 (refus de compiler, agent reformule) plutôt qu'ajouter un second solveur Lean (complexité cumulée type GRAPHE). Escape hatch Lean optionnel = décision différée, à mesurer sur taux réel de blocage.
2. "Vitesse C" nuancée : vrai pour code Perceus-friendly (monomorph.+RC+rustc) ; code à fort partage adversarial reste borné par le RC. À mesurer.
3. Continuations multi-shot (backtracking/probabiliste) = coût réifié sur le tas. Recommandation : opt-in explicite, hors chemin par défaut (le fragment one-shot lexical suffit pour IO/exceptions/état/générateurs/async).
4. Déterminisme total du pretty-printer (texte = fonction pure du graphe, façon gofmt mais plus strict) — contrainte d'implémentation réelle, pas juste cosmétique.
5. `yield` comme mot-clé — verrouillé, cohérent, aucun changement recommandé.
